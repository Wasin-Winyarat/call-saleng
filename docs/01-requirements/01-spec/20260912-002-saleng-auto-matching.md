# ระบบจับคู่คำขอเรียกรถซาเล้งกับสาเล้งในพื้นที่แบบอัตโนมัติ (Auto-Matching)

> **สถานะเอกสาร:** ร่างเริ่มต้น (New) — เป็น **future / next-phase requirement** ที่ยังไม่ถูกกำหนดให้อยู่ใน sprint/module ปัจจุบัน เอกสารนี้บันทึกไอเดียที่ user เสนอไว้ก่อน เพื่อไม่ให้หลุดหายไป และเตรียมไว้สำหรับพัฒนาต่อในรอบถัดไปที่เปิด scope ฝั่งสาเล้ง/matching ยังมี **Open question สำคัญ 1 ข้อที่ user ยังไม่ตัดสินใจ** (ดูหัวข้อ Open questions) ห้าม implement จริงจนกว่าจะยืนยันแล้ว

## บริบท / Background

Requirement นี้ต่อยอด/สืบเนื่องจาก [[20260819-001-saleng-pickup-request|Call-Saleng: ระบบเรียกรถซาเล้งมารับซื้อขยะ Recycle ที่บ้าน]] ซึ่งเป็น requirement หลักของระบบ ในสเปกหลักได้นิยาม flow การจับคู่งานไว้ 2 ช่องทางคือ **self-pick** (สาเล้งกดรับงานเอง) และ **admin-assign** (Admin เลือก assign ให้สาเล้งโดยตรง) — ทั้งสองช่องทางนี้ยังเป็นการทำงาน "manual" ที่สาเล้งต้องมาเปิดดูรายการคำขอที่เปิดอยู่เอง หรือรอ Admin เลือกให้

ระหว่างการคุยเพื่อวางแผนพัฒนาโมดูลปัจจุบัน user เสนอไอเดียเพิ่มเติมว่า อาจใช้ API หรือกลไกจับคู่ซาเล้งที่อยู่ในพื้นที่แบบอัตโนมัติ (โดย GPS หรือตำบลที่สาเล้งลงทะเบียนพื้นที่สนใจไว้) แล้ว "เด้งงาน" ไปแจ้งสาเล้งที่จับคู่ได้ให้กด confirm รับงานเอง แทนที่สาเล้งจะต้องไล่เปิดดูรายการคำขอทั้งหมดเอง

**สำคัญ — ขอบเขตของโมดูลที่กำลังพัฒนาอยู่ในปัจจุบัน:** ตาม `SCOPE.md` และ `CLAUDE.md` ของ repo นี้ โมดูลที่กำลังพัฒนาส่งจริงในรอบนี้ครอบคลุมเฉพาะ **"User สร้างคำขอเรียกรถซาเล้ง" + "Admin accept/cancel/change-time"** เท่านั้น — **ไม่รวม flow ฝั่งสาเล้งเลย** (ไม่มีการลงทะเบียนสาเล้ง, self-pick, admin-assign, หรือ matching ใดๆ implement จริงในโค้ดปัจจุบัน) ดังนั้นฟีเจอร์ auto-matching ที่ระบุในเอกสารนี้จึงอยู่ **นอกขอบเขตของโมดูลปัจจุบันทั้งหมด** และเป็นเพียงการบันทึก requirement ไว้ล่วงหน้าสำหรับรอบพัฒนาถัดไปที่จะเปิด scope ฝั่งสาเล้ง

## Scope

### สิ่งที่ทำ (In scope ของ requirement นี้ — เมื่อถึงรอบพัฒนาจริงในอนาคต)

- เมื่อ Admin confirm คำขอแล้ว (สถานะเปลี่ยนเป็น `open_for_saleng`) ระบบจับคู่คำขอนั้นกับสาเล้งที่อยู่ใน "พื้นที่" เดียวกันโดยอัตโนมัติ โดยมีแนวทางที่เป็นไปได้ 2 แบบ (ยังไม่ตัดสินใจ — ดู Open questions):
  - (ก) จับคู่ตามตำบล (`sub_district`) ที่สาเล้งลงทะเบียนไว้ว่าเป็นพื้นที่สนใจ
  - (ข) จับคู่ด้วยพิกัด GPS ของสาเล้ง ณ ขณะนั้น เทียบกับพิกัด/ที่อยู่ของคำขอ
- ระบบ "เด้งงาน" ไปแจ้งเตือน/แสดงรายการคำขอที่จับคู่ได้ให้สาเล้งที่เกี่ยวข้องเห็น (เช่น sort/filter รายการงานที่เปิดอยู่ให้สาเล้งเห็นเฉพาะ/ก่อนงานในพื้นที่ของตน หรือแจ้งเตือนแบบ push/badge)
- สาเล้งที่ได้รับการจับคู่/แจ้งเตือน ยังต้อง**กด confirm รับงานเอง** ตามกลไก self-pick เดิมที่นิยามไว้ใน [[20260819-001-saleng-pickup-request|requirement หลัก]] — **ระบบนี้ไม่ใช่ auto-assign แบบบังคับมอบหมายงานให้สาเล้งโดยไม่ต้องยินยอม** สาเล้งยังมีสิทธิ์เลือกไม่รับงานที่จับคู่มาให้ได้
- การจับคู่แบบอัตโนมัตินี้เป็นเพียง "ตัวช่วยกรอง/แจ้งเตือน" ที่ทำงานเสริมจากรายการคำขอที่เปิดอยู่ (`open_for_saleng`) เดิม ไม่ได้แทนที่กลไก self-pick/admin-assign ที่มีอยู่แล้ว — สาเล้งยังสามารถเห็นและกดรับงานอื่นนอกพื้นที่ที่จับคู่ได้ตามปกติ (ยังไม่ได้ตัดสินใจว่าจะจำกัดสิทธิ์นี้หรือไม่ — ดู Open questions)

### สิ่งที่ไม่ทำ (Out of scope)

- การ auto-assign แบบบังคับ (ระบบเลือกสาเล้งให้เองโดยไม่ผ่านการกด confirm ของสาเล้ง) — ไม่อยู่ใน scope ตามที่ user เสนอมา (user เสนอแบบ "เด้งงานไปให้สาเล้ง confirm" ไม่ใช่ auto-assign เด็ดขาด)
- การพัฒนาจริงในโมดูล/sprint ปัจจุบัน — ฟีเจอร์นี้ทั้งหมดเป็น future/next-phase ตามที่ระบุในบริบทด้านบน ไม่มี code path ใดใน `webapp/` implement ส่วนนี้ในตอนนี้
- การเลือก API/บริการภายนอกที่ใช้คำนวณระยะทาง/geocoding (ถ้าเลือกแนวทาง GPS) — เป็นรายละเอียดเชิงเทคนิคที่ต้องออกแบบในขั้น [[../../02-design/02-technical/index|02-technical]] เมื่อ requirement นี้ถูกยืนยันแล้ว ไม่ใช่ส่วนของสเปกนี้
- ระบบให้คะแนน/จัดลำดับความสำคัญของสาเล้งในการจับคู่ (เช่น สาเล้งสมาชิกได้เห็นงานก่อน) — เป็นคนละเรื่องกับ `membership_tier` ที่ระบุไว้ใน [[../../02-design/02-technical/database-schema|database-schema]] แล้ว (future scope อีกเรื่องหนึ่ง ไม่ได้รวมไว้ในสเปกนี้)

## User stories / Use cases

1. **ในฐานะ Admin** เมื่อฉัน confirm คำขอของ user แล้ว ฉันต้องการให้ระบบช่วยจับคู่และแจ้งเตือนคำขอนั้นไปยังสาเล้งในพื้นที่โดยอัตโนมัติ เพื่อลดภาระที่สาเล้งต้องมานั่งไล่ดูรายการคำขอทั้งหมดเอง และลดโอกาสที่คำขอค้างนานเพราะไม่มีสาเล้งเห็น
2. **ในฐานะสาเล้ง** ฉันต้องการได้รับการแจ้งเตือน/เห็นคำขอที่อยู่ในพื้นที่ที่ฉันสนใจ (ตามตำบลที่ลงทะเบียน หรือตามตำแหน่ง GPS ปัจจุบันของฉัน) เพื่อให้ฉันเห็นงานที่คุ้มค่าเดินทางได้เร็วขึ้น โดยไม่ต้องไล่ดูคำขอนอกพื้นที่ที่ไม่สะดวกไปรับ
3. **ในฐานะสาเล้ง** เมื่อระบบจับคู่/แจ้งเตือนงานมาให้ ฉันยังต้องการสิทธิ์เลือกกด confirm รับงานเองอีกครั้ง เพื่อให้ฉันยังควบคุมได้ว่าจะรับงานนั้นจริงหรือไม่ (ไม่ถูกมอบหมายงานอัตโนมัติโดยไม่ยินยอม)

## Business rules / เงื่อนไข

- การจับคู่อัตโนมัติเกิดขึ้น**หลังจาก** Admin confirm คำขอแล้วเท่านั้น (สถานะ `pickup_request.status` เปลี่ยนเป็น `open_for_saleng`) — สอดคล้องกับ flow ที่นิยามไว้ใน [[20260819-001-saleng-pickup-request|requirement หลัก]] ว่าคำขอต้องผ่าน Admin review ก่อนเปิดให้สาเล้งเห็น/รับงานได้
- การจับคู่แบบอัตโนมัติ**ไม่ทำให้สถานะคำขอเปลี่ยนเป็น final ทันที** — ยังต้องผ่านกลไก self-pick (สาเล้งกด confirm รับงาน) และ Admin confirm ขั้นสุดท้ายกับ user ตาม business rule เดิมของ [[20260819-001-saleng-pickup-request|requirement หลัก]] ("คำขอต้องผ่านการ confirm จาก Admin กับ user เป็นขั้นสุดท้ายเสมอ")
- คำขอ 1 รายการยังคงผูกกับสาเล้งได้เพียง 1 คนเท่านั้นตามเดิม (ป้องกันรับงานซ้ำ) — การจับคู่อัตโนมัติเป็นเพียงชั้นการกรอง/แจ้งเตือนที่ทำงานอยู่เหนือ business rule นี้ ไม่เปลี่ยนแปลงกติกาการกันงานซ้ำที่มีอยู่แล้ว

## สถานะการเตรียมพร้อมเชิงข้อมูล (สืบเนื่องจาก database-schema)

- [[../../02-design/02-technical/database-schema|database-schema]] มีร่องรอยการเผื่อออกแบบแนวทาง **ตำบล (`sub_district`)** ไว้แล้วในระดับ data model — field `sub_district` ถูกเพิ่มไว้ทั้งใน `user_address` และ `pickup_request` พร้อมหมายเหตุระบุชัดว่าเผื่อไว้สำหรับ "สาเล้งกรองรายการคำขอในพื้นที่ที่สนใจ" (ดูหัวข้อ "สมมติฐานและข้อจำกัด" และ "คำถามเปิด" ข้อ 6 ของเอกสารนั้น) กล่าวคือแนวทางจับคู่ตามตำบลถูกคิดไว้เป็นทางเลือกหนึ่งแล้วในระดับ data model
- ในทางกลับกัน **แนวทาง GPS ของสาเล้ง** ยังไม่มีร่องรอยใดๆ ในสคีมาปัจจุบันเลย — มีเพียง `gps_latitude`/`gps_longitude` ของ **ที่อยู่/คำขอฝั่ง user** เท่านั้น (ใน `user_address` และ `pickup_request`) ไม่มี field พิกัด GPS ของ `saleng_account` เลย หากเลือกแนวทางนี้ต้องออกแบบ schema เพิ่มเติมทั้งหมด (เช่น พิกัดปัจจุบันของสาเล้ง, ความถี่ในการอัปเดตพิกัด, รัศมีการค้นหา ฯลฯ)
- ปัจจุบัน **ยังไม่มี** collection/table สำหรับ `saleng_account` และ `request_match` ที่ implement จริงในโค้ด `webapp/` ของโปรเจกต์ (มีเพียงชื่อตารางที่ระบุไว้ใน [[../../02-design/02-technical/database-schema|database-schema]] ว่าเป็นตารางที่ "ยังไม่ implement" ตาม `CLAUDE.md`) ดังนั้น requirement นี้ต้องรอทั้งการ implement บัญชีสาเล้งและตาราง matching ก่อน จึงจะเริ่มพัฒนาส่วน auto-matching นี้ได้จริง

## Open questions

1. **จะเลือกจับคู่คำขอกับสาเล้งด้วยวิธีใด** — ยังไม่ได้ตัดสินใจ ต้องยืนยันกับ user ในรอบถัดไปก่อนเริ่มออกแบบเชิงเทคนิค:
   - **(ก) ใช้ตำบล (`sub_district`)** — ข้อดี: มีร่องรอยเผื่อไว้แล้วใน data model ปัจจุบัน (`sub_district` field ใน `user_address`/`pickup_request`), ไม่ต้องพึ่งพา GPS permission จากสาเล้ง (ซึ่งอาจถูกปฏิเสธ/ไม่แม่นยำเวลาอยู่ในอาคาร), implement ง่ายกว่า (string matching) ข้อเสีย: หยาบกว่า ไม่ได้สะท้อนตำแหน่งจริง ณ ขณะนั้นของสาเล้ง (เช่น สาเล้งอาจกำลังขับอยู่นอกตำบลที่ลงทะเบียนไว้)
   - **(ข) ใช้พิกัด GPS** — ข้อดี: แม่นยำกว่า สะท้อนตำแหน่งจริงของสาเล้ง ณ ขณะนั้น รองรับการคำนวณระยะทาง/จัดลำดับความใกล้ได้ ข้อเสีย: ต้องออกแบบ schema/flow ใหม่ทั้งหมด (ยังไม่มีร่องรอยใดๆ ในสคีมาปัจจุบัน), ต้องพึ่งพา GPS permission และแบตเตอรี่ของอุปกรณ์สาเล้ง, ซับซ้อนกว่าในการ implement (คำนวณระยะทาง/รัศมี, ต้องมี API หรือ library ภายนอก)
   - **(ค) ใช้ทั้งสองแบบร่วมกัน (fallback)** — ข้อดี: ยืดหยุ่นที่สุด เช่น ใช้ GPS เป็นหลักถ้ามีพิกัด ใช้ `sub_district` เป็น fallback ถ้าไม่มี/ปิด GPS ข้อเสีย: ซับซ้อนที่สุดในการออกแบบและ implement (ต้องดูแล 2 เส้นทางข้อมูลพร้อมกัน), อาจทำให้ผลการจับคู่ไม่สอดคล้องกันระหว่างสาเล้งที่ใช้คนละวิธี
   - user ยังไม่ได้ตัดสินใจเรื่องนี้ในบทสนทนาที่ผ่านมา — **agent นี้จะไม่ตัดสินใจแทน** ต้องยืนยันกับ user ก่อนจึงจะแตกไปเป็น [[../02-plan/index|02-plan]] หรือ [[../../02-design/02-technical/index|02-technical]] ต่อได้
2. หากเลือกแนวทาง GPS หรือ hybrid ในข้อ 1 — สาเล้งต้องเปิด GPS/แชร์พิกัดตลอดเวลาที่ออนไลน์ในระบบ หรือกดรีเฟรชพิกัดเป็นครั้งคราวเมื่อต้องการดูงาน (ผลต่อ battery/privacy) ยังไม่ได้พูดคุยประเด็นนี้
3. รัศมี/ขอบเขตของ "พื้นที่ใกล้เคียง" ที่ถือว่าจับคู่ได้ (เช่น กี่กิโลเมตรจากพิกัดสาเล้ง หรือเฉพาะตำบลเดียวกันเท่านั้น) ยังไม่ได้ระบุ
4. เมื่อจับคู่ได้สาเล้งหลายคนพร้อมกันในพื้นที่เดียวกัน ระบบจะแจ้งเตือนทุกคนพร้อมกันแบบ first-come-first-served (ตาม self-pick เดิม) หรือมีลำดับความสำคัญ (เช่น ตาม `membership_tier` ในอนาคต) ยังไม่ได้ระบุ

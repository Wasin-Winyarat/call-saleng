# ระบบจับคู่งานสาเล้งตามพื้นที่ (ตำบล) + Admin-assign และการจัดการสาเล้ง (เดิมชื่อ "Auto-Matching")

> **สถานะเอกสาร:** Confirmed — ปิด Open questions เดิมครบทุกข้อแล้ว (user ยืนยันข้อสรุปทั้งหมดในแชทวันที่ 2026-11-07) และ **เปิด scope ฝั่งสาเล้งในรอบพัฒนานี้แล้ว** (user สั่งให้เริ่มพัฒนาหน้าซาเล้ง) พร้อมแตกไปเป็น [[../02-plan/index|02-plan]] และ [[../../02-design/02-technical/index|02-technical]]
>
> **ประวัติ:** สร้าง 2026-09-12 เป็นไอเดีย future/next-phase "จับคู่อัตโนมัติด้วย GPS หรือตำบล แล้วเด้งงานให้สาเล้ง confirm" — อัปเดต 2026-11-07: user เลือกจับคู่ **ตามตำบล (`sub_district`) + Admin-assign (manual)** ร่วมกัน และ**ตัด GPS ออก**จากขอบเขตตอนนี้ จึงไม่ใช่ "auto-matching" ในความหมายเดิมแล้ว ชื่อไฟล์คงไว้เหมือนเดิมเพื่อไม่ให้ wikilink ที่อ้างถึงเสีย พร้อมขยายเนื้อหาให้ครอบคลุมการอนุมัติสาเล้ง, โควตาคิว, กติกาการยกเลิกของสาเล้ง และแชท Admin–สาเล้ง

## บริบท / Background

Requirement นี้ต่อยอดจาก [[20260819-001-saleng-pickup-request|Call-Saleng: ระบบเรียกรถซาเล้งมารับซื้อขยะ Recycle ที่บ้าน]] (requirement หลัก) ซึ่งนิยาม flow การจับคู่งานไว้ 2 ช่องทางคือ **self-pick** (สาเล้งกดรับงานเอง) และ **admin-assign** (Admin assign ให้สาเล้งโดยตรง) โดยทุกกรณีต้องผ่าน **Admin confirm เป็นขั้นสุดท้าย** เอกสารนี้ไม่เปลี่ยนหลักการทั้งสามข้อนั้น แต่ลงรายละเอียดว่า:

- สาเล้งเห็นงานใดได้บ้าง (กรองตามตำบลที่ลงทะเบียน)
- Admin assign งานอย่างไร (รวมงานนอกตำบลของสาเล้ง) และสาเล้งต้องตอบรับก่อน
- สาเล้งรับงานได้กี่งาน (โควตาคิว) และยกเลิกงานได้ถึงเมื่อไร
- สาเล้งสมัครเข้าร่วมและได้รับการอนุมัติอย่างไร

เดิม user เสนอไอเดียจับคู่อัตโนมัติด้วย GPS หรือตำบลแล้ว "เด้งงาน" ให้สาเล้ง ในการคุยวันที่ 2026-11-07 user ตัดสินใจว่า **"ฉันเลือก 1+3 เรื่อง gps ตัดทิ้งก่อน"** คือใช้ตำบล + admin assign และอาจพิจารณา GPS ในอนาคตเป็นเพียงการเรียงงานตามระยะทาง

**ขอบเขตรอบพัฒนา:** เดิมเอกสารนี้ระบุว่าทั้งฟีเจอร์ "อยู่นอกขอบเขตโมดูลปัจจุบัน" ตาม `SCOPE.md` (ที่ครอบคลุมเฉพาะ user สร้างคำขอ + admin accept/cancel/change-time) — **ณ 2026-11-07 user สั่งให้เริ่มพัฒนาหน้าซาเล้งแล้ว** ดังนั้นฝั่งสาเล้งตามเอกสารนี้ถือว่า **อยู่ใน scope ของรอบพัฒนานี้** (หมายเหตุ: `SCOPE.md` และ `CLAUDE.md` ที่ root ยังเขียนว่าฝั่งสาเล้งอยู่นอกขอบเขต ต้องปรับให้สอดคล้องในภายหลัง — ดูหัวข้อ "ผลกระทบต่อเอกสารอื่น")

## Scope

### สิ่งที่ทำ (In scope — รอบพัฒนานี้)

**ก. การสมัครและอนุมัติสาเล้ง**
- สาเล้งสมัครด้วยข้อมูล: ชื่อ, เบอร์โทร, ทะเบียนรถ, รูปรถ, รูปบัตรประชาชน, และตำบลที่รับงาน (เลือกได้หลายตำบล)
- บัญชีใหม่อยู่สถานะ `pending_approval` → Admin ตรวจข้อมูลแล้ว approve หรือ reject (reject ต้องระบุเหตุผล) → `approved` จึงรับงานได้
- Admin ระงับบัญชี (`suspended`) ได้ภายหลัง
- ระหว่างรออนุมัติ สาเล้ง login ได้แต่ยังไม่เห็นงานใดๆ

**ข. การมองเห็นงานและการจับคู่**
- สาเล้งที่ `approved` เห็นเฉพาะคำขอสถานะ `open_for_saleng` ที่ `sub_district` ตรงกับตำบลที่ตนลงทะเบียนรับงานเท่านั้น และกดรับงานเอง (self-pick) ได้
- งานในตำบลอื่นที่สาเล้งไม่ได้ลงทะเบียน จะไปถึงสาเล้งได้ทางเดียวคือ **Admin assign**
- Admin assign งานให้สาเล้งคนใดก็ได้ (ไม่จำกัดตำบล) โดยหน้าจอ assign แสดงรายชื่อสาเล้งเรียงตาม (1) ตำบลตรงกับงานก่อน แล้ว (2) จำนวนงานในรอบนั้นน้อยไปมาก พร้อมแสดงโควตาของแต่ละคนในรอบนั้น
- งานที่ถูก assign สาเล้งต้องกด **"ตอบรับ"** หรือ **"ปฏิเสธ"** ก่อน — ถ้าตอบรับจึงไปรอ Admin confirm
- Admin dashboard แจ้งเตือนงานที่อยู่ในตำบลที่ไม่มีสาเล้ง (approved) ลงทะเบียนไว้ และงานที่ค้างอยู่นาน

**ค. Admin confirm ขั้นสุดท้ายและแชท Admin–สาเล้ง**
- ยังคงมี Admin confirm ขั้นสุดท้ายทุกกรณี (user: "ควรจะมีดีกว่า เผื่อมีการแชทคุยระหว่างซาเล้งกับ admin")
- ระหว่าง `pending_match_confirm` Admin กับสาเล้งแชทกันได้ — เป็นห้องแชทแยกจากแชท Admin–ลูกค้า
- แชท Admin–สาเล้งยังใช้ต่อหลัง confirm สำหรับ "ขอยกเลิกผ่าน Admin" (ดู Business rules ข้อการยกเลิก)

**ง. โควตาคิว**
- จำกัดไม่เกิน 3 งานต่อรอบ (วันเดียวกัน + ช่วงเวลาเดียวกัน) และไม่เกิน 6 งานที่รับแล้วยังไม่เสร็จรวมทุกวัน (รายละเอียดใน Business rules)

**จ. การยกเลิกของสาเล้ง**
- สาเล้งยกเลิกงานที่รับไว้ได้ตามกำหนดเวลา, ต้องระบุเหตุผล, งานกลับไปเป็น `open_for_saleng` และลูกค้าเห็นแจ้งเตือนว่ากำลังหาซาเล้งใหม่
- ระบบนับสถิติการยกเลิกกระชั้นชิดของสาเล้งแต่ละคนให้ Admin ใช้ประกอบการพิจารณาระงับบัญชี

**ฉ. แพลตฟอร์มฝั่งสาเล้ง**
- ใช้บน smartphone เป็นหลัก (Web App แบบ responsive — สอดคล้องกับแพลตฟอร์มของ requirement หลัก)

### สิ่งที่ไม่ทำ (Out of scope)

- **การจับคู่/กรองงานด้วย GPS** — ตัดออกจากขอบเขตตอนนี้ (อาจพิจารณาในอนาคตเป็นเพียงการเรียงงานตามระยะทาง ไม่ใช่เงื่อนไขการมองเห็นงาน)
- **Auto-assign แบบบังคับ** — ระบบไม่เลือกสาเล้งให้เองโดยอัตโนมัติ ทุกงานต้องผ่านการกดรับ/ตอบรับของสาเล้ง และ Admin confirm
- การจัดลำดับความสำคัญของสาเล้งตาม `membership_tier` (เช่น สมาชิกเห็นงานก่อน) — เป็น future scope แยกต่างหาก
- การใช้รูปบัตรประชาชนจริงในระบบทดสอบ — ระบบทดสอบใช้รูปจำลองเท่านั้น
- การเลือกเทคโนโลยี/บริการภายนอกใดๆ — เป็นงานของ [[../../02-design/02-technical/index|02-technical]]

## User stories / Use cases

1. **ในฐานะสาเล้งที่สมัครใหม่** ฉันต้องการกรอกชื่อ, เบอร์โทร, ทะเบียนรถ, รูปรถ, รูปบัตรประชาชน และเลือกตำบลที่รับงาน (ได้หลายตำบล) เพื่อยื่นให้ Admin ตรวจสอบก่อนเข้าร่วม — ระหว่างรออนุมัติฉัน login ได้แต่ยังไม่เห็นงาน
2. **ในฐานะ Admin** ฉันต้องการตรวจข้อมูลสาเล้งที่สมัครเข้ามาแล้ว approve หรือ reject พร้อมเหตุผล และระงับบัญชีได้ภายหลัง เพื่อควบคุมคุณภาพผู้ให้บริการ
3. **ในฐานะสาเล้ง** ฉันต้องการเห็นเฉพาะงานที่เปิดอยู่ในตำบลที่ฉันลงทะเบียน เพื่อไม่ต้องไล่ดูงานนอกพื้นที่ และกดรับงานได้เองถ้าคิวยังไม่เต็ม
4. **ในฐานะสาเล้ง** เมื่อคิวของรอบนั้นเต็มแล้ว ฉันต้องการเห็นว่าคิวเต็ม (เช่น "คิวเต็ม 3/3") และกดรับงานเพิ่มในรอบนั้นไม่ได้ เพื่อไม่รับงานเกินกำลังหรือเวลาชนกัน
5. **ในฐานะ Admin** ฉันต้องการ assign งาน (รวมถึงงานในตำบลที่ไม่มีสาเล้ง) ให้สาเล้งคนใดก็ได้ โดยเห็นรายชื่อที่เรียงตำบลตรงก่อนและคิวน้อยก่อน พร้อมโควตาของแต่ละคนในรอบนั้น และถ้าคิวเต็มให้เตือนแต่ยัง override ได้
6. **ในฐานะสาเล้ง** เมื่อ Admin assign งานมาให้ ฉันต้องการกด "ตอบรับ" หรือ "ปฏิเสธ" ได้ก่อน เพื่อยังควบคุมได้ว่าจะรับงานนั้นจริงหรือไม่
7. **ในฐานะ Admin** หลังสาเล้งรับ/ตอบรับงานแล้ว ฉันต้องการแชทกับสาเล้ง (แยกจากแชทลูกค้า) ก่อน confirm ขั้นสุดท้าย เพื่อตกลงรายละเอียดให้ชัด
8. **ในฐานะ Admin** ฉันต้องการเห็นแจ้งเตือนบน dashboard สำหรับงานในตำบลที่ไม่มีสาเล้ง และงานที่ค้างนาน เพื่อเข้าไป assign ได้ทันเวลา
9. **ในฐานะสาเล้ง** ฉันต้องการยกเลิกงานที่รับไว้ได้เองภายในกำหนดเวลา (ระบุเหตุผล) และถ้าเลยกำหนดให้ขอยกเลิกผ่าน Admin ทางแชท
10. **ในฐานะลูกค้า (user)** เมื่อสาเล้งยกเลิกงานของฉัน ฉันต้องการเห็นแจ้งเตือนว่าระบบกำลังหาซาเล้งใหม่ เพื่อรู้สถานะและไม่ต้องสร้างคำขอใหม่
11. **ในฐานะ Admin** ฉันต้องการเห็นสถิติการยกเลิกกระชั้นชิดของสาเล้งแต่ละคน เพื่อใช้ประกอบการตัดสินใจระงับบัญชี

## Business rules / เงื่อนไข

### 1. วิธีจับคู่และการมองเห็นงาน
- จับคู่ด้วย **ตำบล (`sub_district`)** + **Admin-assign (manual)** ร่วมกัน ไม่ใช้ GPS
- สาเล้ง 1 คนลงทะเบียนตำบลที่รับงานได้หลายตำบล
- สาเล้งเห็นเฉพาะคำขอสถานะ `open_for_saleng` ที่ `sub_district` ของคำขอตรงกับตำบลที่ตนลงทะเบียนไว้ (user: "เห็นแค่ตำบลตัวเอง (ถ้าเป็นตำบลอื่น ต้องเป็น admin assign งานไปให้)")
- สาเล้งที่ไม่ได้อยู่สถานะ `approved` (คือ `pending_approval`, `rejected`, `suspended`) ไม่เห็นงานและรับงานไม่ได้
- คำขอ 1 รายการผูกกับสาเล้งได้เพียง 1 คน และหายไปจากรายการของสาเล้งคนอื่นทันทีเมื่อมีผู้รับแล้ว (ตาม requirement หลัก)
- การเข้าถึงงานเกิดขึ้นหลัง Admin review คำขอแล้วเท่านั้น (สถานะ `open_for_saleng`)

### 2. สถานะคำขอ (`pickup_request.status`)
```
pending_admin_review → open_for_saleng → pending_match_confirm → confirmed → completed
                                                     (cancelled ได้ตาม rule ของ requirement หลัก)
```
- **Self-pick:** สาเล้งกดรับงาน → `pending_match_confirm` → Admin confirm → `confirmed`
- **Admin-assign:** Admin assign → สาเล้งกด "ตอบรับ" → `pending_match_confirm` → Admin confirm → `confirmed` / ถ้าสาเล้งกด "ปฏิเสธ" งานยังคงเปิดรอผู้รับ (`open_for_saleng`)
- ระหว่าง `pending_match_confirm` Admin กับสาเล้งแชทกันได้ (ห้องแยกจากแชทลูกค้า)

### 3. การ assign ของ Admin
- Admin assign งานให้สาเล้งที่ `approved` คนใดก็ได้ ไม่จำกัดตำบล
- รายชื่อสาเล้งตอน assign เรียงตาม: (1) ตำบลที่ลงทะเบียนตรงกับ `sub_district` ของงานก่อน, (2) จำนวนงานในรอบเดียวกับงานนั้น น้อยไปมาก
- แสดงโควตาของสาเล้งแต่ละคนในรอบนั้น (เช่น 2/3) ถ้าเต็มขึ้นคำเตือน แต่ Admin ยัง override ได้

### 4. โควตาคิวของสาเล้ง
- **ไม่เกิน 3 งานต่อรอบ** — "รอบ" คือวันเดียวกัน (`requested_date`) + ช่วงเวลาเดียวกัน (`time_slot`: 08:00–13:00 หรือ 13:00–18:00)
- **ไม่เกิน 6 งานที่รับแล้วแต่ยังไม่เสร็จ รวมทุกวัน** (นับงานสถานะ `pending_match_confirm` และ `confirmed` ที่ผูกกับสาเล้งคนนั้น)
- สาเล้งกดรับงาน (self-pick) ที่จะทำให้เกินโควตาไม่ได้ — ปุ่มรับงานแสดงสถานะคิวเต็ม (เช่น "คิวเต็ม 3/3")
- Admin override โควตาได้ตอน assign (มีคำเตือน) ตามข้อ 3
- จุดประสงค์คือกันการรับงานมากเกินกำลังและกันเวลานัดชนกันของสาเล้งคนเดียว (user: "ตรวจสอบเวลาจ่ายงานด้วยว่างานที่จะส่งให้เวลาซ้ำกับ order ที่ซาเล้งมีอยู่แล้วหรือไม่")

### 5. การยกเลิกงานของสาเล้ง
- งานที่สาเล้งยกเลิก **กลับเป็น `open_for_saleng`** ให้สาเล้งคนอื่นรับใหม่ได้ (ไม่ใช่ `cancelled`)
- **ก่อน Admin confirm** (`pending_match_confirm`) — สาเล้งยกเลิกได้อิสระ
- **หลัง Admin confirm** (`confirmed`) — สาเล้งยกเลิกเองได้ถึงเวลา:

  ```
  กำหนดยกเลิกได้ = เวลาเริ่มรอบนัด − min(6 ชั่วโมง, (เวลาเริ่มรอบนัด − เวลาที่กดรับ) / 2)
  ```
  - เวลาเริ่มรอบนัด = 08:00 (รอบเช้า) หรือ 13:00 (รอบบ่าย) ของวันนัด
  - ตัวอย่าง 1: กดรับวันก่อนหน้า 15:00 นัดวันถัดไปรอบ 13:00 (ห่าง 22 ชม. ครึ่งหนึ่ง = 11 ชม. → ใช้ 6 ชม.) → ยกเลิกเองได้ถึง **07:00**
  - ตัวอย่าง 2: กดรับ 10:00 นัดรอบ 13:00 วันเดียวกัน (ห่าง 3 ชม. ครึ่งหนึ่ง = 1.5 ชม.) → ยกเลิกเองได้ถึง **11:30**
  - เหตุผลของสูตรนี้: user ต้องการกันการยกเลิกกระชั้นชิด ("ไม่ใช่ว่ายกเลิกก่อนลูกค้านัด 10 นาที") แต่ต้อง "คิดเผื่อกรณีลูกค้าส่งคำขอช่วงเช้าแล้วให้เข้าไปรับช่วงบ่ายเลย" ซึ่งเวลาห่างไม่ถึง 6 ชม.
- เลยกำหนดแล้ว สาเล้งยกเลิกเองไม่ได้ ต้อง **"ขอยกเลิกผ่าน Admin"** ทางแชท Admin–สาเล้ง
- การยกเลิกทุกกรณีต้องระบุเหตุผล
- ระบบนับสถิติการยกเลิกกระชั้นชิดต่อสาเล้งให้ Admin ใช้ประกอบการระงับบัญชี
- เมื่อสาเล้งยกเลิก ลูกค้าเห็นแจ้งเตือนว่ากำลังหาซาเล้งใหม่

### 6. การสมัครและสถานะบัญชีสาเล้ง
- สถานะบัญชี: `pending_approval` → `approved` / `rejected` (reject ต้องมีเหตุผล) และ `approved` → `suspended` ได้ภายหลัง
- ข้อมูลสมัคร: ชื่อ, เบอร์โทร, ทะเบียนรถ, รูปรถ, รูปบัตรประชาชน, ตำบลที่รับงาน (หลายตำบล)
- ระหว่าง `pending_approval` login ได้แต่ไม่เห็นงาน
- **รูปบัตรประชาชนเป็นข้อมูลอ่อนไหว:** สิทธิ์อ่านจำกัดเฉพาะเจ้าของบัญชีและ Admin; ระบบทดสอบใช้รูปจำลองเท่านั้น ห้ามอัปโหลดบัตรประชาชนจริง (user: "ควรจะมีนะ แต่ระบบเทสก็ไม่ได้อัพรูปบัตรประชาชนจริงเข้าไป")

### 7. แพลตฟอร์ม
- ฝั่งสาเล้งออกแบบให้ใช้บน smartphone เป็นหลัก (Web App responsive)

## ผลกระทบต่อเอกสารอื่น (ข้อ 1–5 และ 7 แก้แล้ว 2026-11-07 — ข้อ 6 ยังติดตาม)

ข้อสรุปข้างต้นไม่ขัดกับหลักการใน [[20260819-001-saleng-pickup-request|requirement หลัก]] (self-pick + admin-assign + Admin confirm ขั้นสุดท้าย) แต่มีบางจุดที่เอกสารหลักควรปรับให้สอดคล้อง ตามคำสั่งให้**บันทึกไว้ที่นี่แทนการแก้ spec หลักโดยตรง**:

> **อัปเดต 2026-11-07:** ข้อ 1–5 (จุดที่ spec หลักต้องปรับ) **ปรับใน [[20260819-001-saleng-pickup-request|spec 001]] แล้ว (2026-11-07)** — ข้อ 7 (database-schema) อัปเดตแล้ว (2026-11-07) — ข้อ 6 (`SCOPE.md` / `CLAUDE.md`) ยังติดตาม

1. **ระดับการยืนยันตัวตนสาเล้ง (ขัดกับ spec หลักโดยตรง)** — spec หลักระบุ "การยืนยันตัวตนสาเล้งใน MVP ใช้เบอร์โทร/OTP เท่านั้น ไม่ต้องอัปโหลดเอกสารทะเบียนรถหรือบัตรประชาชน" และใส่ "KYC/เอกสารทะเบียนรถ, บัตรประชาชน" ไว้ใน Out of scope — ข้อสรุปใหม่ (user ยืนยันแล้ว) **เพิ่มทะเบียนรถ, รูปรถ และรูปบัตรประชาชนในการสมัคร** ให้ Admin ตรวจก่อนอนุมัติ → spec หลักควรอัปเดต business rule และ out of scope ข้อนี้
2. **ขั้นตอน admin-assign** — spec หลักเขียนว่า "(1) Admin confirm การจับคู่กับสาเล้งที่เลือกก่อน แล้ว (2) Admin confirm กับ user" ข้อสรุปใหม่ทำขั้น (1) ให้ชัดขึ้นเป็น "สาเล้งกดตอบรับ/ปฏิเสธในระบบ" → ไม่ขัดกันในหลักการ แต่ควรปรับถ้อยคำให้ตรงกัน
3. **การมองเห็นงานของ self-pick** — spec หลักระบุ "ดูรายการคำขอที่เปิดอยู่ในพื้นที่ที่ตนสนใจ" ข้อสรุปใหม่ทำให้เข้มขึ้นเป็น "เห็นเฉพาะตำบลที่ลงทะเบียนเท่านั้น งานตำบลอื่นต้องผ่าน admin-assign" → สอดคล้อง แต่ควรระบุให้ชัด
4. **การยกเลิกของสาเล้ง** — spec หลักระบุ "User หรือ saleng สามารถยกเลิกคำขอได้ก่อนงานเสร็จสิ้น" ข้อสรุปใหม่เพิ่มกำหนดเวลายกเลิก, การยกเลิกผ่าน Admin และการคืนงานเป็น `open_for_saleng` (ไม่ใช่ปิดคำขอ) → ควรเพิ่มอ้างอิงมาที่เอกสารนี้
5. **โควตาคิวและแชท Admin–สาเล้ง** — เป็น rule ใหม่ที่ไม่มีใน spec หลัก (เพิ่ม ไม่ขัด)
6. **`SCOPE.md` / `CLAUDE.md` ที่ root** — ยังระบุว่าฝั่งสาเล้ง/matching อยู่นอกขอบเขต ต้องปรับตามการเปิด scope ฝั่งสาเล้งรอบนี้
7. **[[../../02-design/02-technical/database-schema|database-schema]]** (**อัปเดตแล้ว 2026-11-07** — ดู [[../../05-log/20261107-log|log 2026-11-07]]) — ต้องรองรับ: สถานะบัญชีสาเล้ง (`pending_approval`/`approved`/`rejected`/`suspended`) + เหตุผล reject, ทะเบียนรถ/รูปรถ/รูปบัตรประชาชน, ตำบลที่รับงานหลายค่า, สถานะการตอบรับงานที่ถูก assign, เวลาที่กดรับ (ใช้คำนวณกำหนดยกเลิก), เหตุผล/ประวัติการยกเลิกของสาเล้ง, และห้องแชท Admin–สาเล้ง

## สถานะการเตรียมพร้อมเชิงข้อมูล (สืบเนื่องจาก database-schema)

- [[../../02-design/02-technical/database-schema|database-schema]] มี `sub_district` อยู่แล้วทั้งใน `user_address` และ `pickup_request` (เผื่อไว้สำหรับให้สาเล้งกรองงานตามพื้นที่) — รองรับแนวทางที่เลือกได้ทันที
- เนื่องจากตัด GPS ออก จึงไม่ต้องเพิ่ม field พิกัดของ `saleng_account` ในรอบนี้
- `saleng_account` และ `request_match` ยังไม่ implement ในโค้ด `webapp/` — ต้องสร้างในรอบพัฒนานี้ (ดูรายการที่ต้องเพิ่มในหัวข้อ "ผลกระทบต่อเอกสารอื่น" ข้อ 7)

### ประเด็นที่ต้องติดตามต่อ (รายละเอียดระดับออกแบบ — ไม่ใช่ประเด็นเชิงนโยบาย)

- เกณฑ์ "งานค้างนาน" ที่ Admin dashboard ใช้เตือน (กี่ชั่วโมง/นับจากสถานะใด) ยังไม่ได้กำหนดตัวเลข
- นิยามละเอียดของ "การยกเลิกกระชั้นชิด" ที่นับในสถิติ (เช่น นับเฉพาะที่ขอผ่าน Admin หลังเลยกำหนด หรือนับทุกการยกเลิกหลัง confirm) และเกณฑ์ที่ใช้พิจารณาระงับบัญชี
- ถ้า Admin เปลี่ยนวันที่/ช่วงเวลานัด (`requested_date`/`time_slot`) ของงานที่สาเล้งรับไว้แล้ว — กำหนดเวลายกเลิกคำนวณใหม่จากรอบนัดใหม่หรือไม่ และนับโควตารอบใหม่อย่างไร
- สำหรับงาน admin-assign "เวลาที่กดรับ" ในสูตรกำหนดยกเลิก ใช้เวลาที่สาเล้งกด "ตอบรับ" (สันนิษฐานตามถ้อยคำ "ตั้งแต่กดรับ" — ควรยืนยันตอนออกแบบ)
- ระหว่างที่งานถูก assign แต่สาเล้งยังไม่ตอบรับ งานนั้นถูกกันไว้จากสาเล้งคนอื่นหรือไม่ และมีเวลาหมดอายุของการรอตอบรับหรือไม่
- ~~วิธี login ของสาเล้ง (OTP ตาม spec หลัก หรือ pattern เบอร์โทร/รหัสผ่านแบบเดียวกับ user ในโค้ดปัจจุบัน)~~ — **ปิดแล้ว (2026-11-07):** ใช้เบอร์โทร + รหัสผ่าน ไม่ใช้ OTP ใน MVP (ตาม [[20260819-001-saleng-pickup-request|spec 001]] ที่แก้แล้ว)
- การแจ้งเตือนงานใหม่แบบ push/badge ให้สาเล้ง (แนวคิด "เด้งงาน" เดิม) — ยังไม่ได้ระบุว่าอยู่ในรอบนี้หรือไม่ ขั้นต่ำคือรายการงานที่กรองตามตำบล

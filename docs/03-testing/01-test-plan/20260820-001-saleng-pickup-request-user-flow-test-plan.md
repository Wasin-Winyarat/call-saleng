## ขอบเขตการทดสอบ (In Scope / Out of Scope)

**In Scope** (เฉพาะฝั่ง User ตามที่ orchestrator กำหนด):
- สมัครสมาชิก/เข้าสู่ระบบด้วยเบอร์โทร + OTP
- หน้าแรก (Home) — CTA เริ่มสร้างคำขอ, quick-link, รายการคำขอที่กำลังดำเนินการ
- เลือก/กรอกที่อยู่ + ตรวจสอบพื้นที่ให้บริการ (เขตอำเภอเมือง เชียงราย)
- กรอกฟอร์มคำขอ (ข้อมูลติดต่อ, วันที่/ช่วงเวลา, ประเภทขยะ/ปริมาณ, อัปโหลดรูปสูงสุด 5 ภาพ)
- ดูราคากลางอ้างอิงต่อกิโลกรัม (ทั้งในฟอร์มคำขอและหน้าราคาขยะ)
- ดูสถานะคำขอ (timeline ครบทุกสถานะ) และยกเลิกคำขอก่อนงานเสร็จสิ้น
- หน้าติดตามรายการคำขอทั้งหมด (list + filter)
- หน้าโปรไฟล์ (แก้ไขข้อมูลส่วนตัว, จัดการที่อยู่ที่บันทึกไว้, ออกจากระบบ)
- ดูใบเสร็จหลังงานเสร็จสิ้น (รวม breakdown ค่าธรรมเนียม 20 บาท/คำขอ)
- แชทกับ Admin เกี่ยวกับคำขอของตัวเอง

**Out of Scope** (ไม่แตก test case ในเอกสารนี้ แม้อยู่ใน spec เดียวกัน):
- Business logic ฝั่ง Saleng ล้วนๆ (รับงาน self-pick, ส่งใบเสร็จ, settle ค่าธรรมเนียม)
- Business logic ฝั่ง Admin ล้วนๆ (confirm/assign งาน, อนุมัติ/ระงับบัญชีสาเล้ง, ตั้ง/แก้ไขราคากลาง, แชทฝั่ง Admin)
- ระบบชำระเงินออนไลน์, ระบบให้คะแนน/รีวิว, การจองล่วงหน้าแบบ recurring, push notification real-time, พื้นที่ให้บริการนอกเขตอำเภอเมืองเชียงราย — ตามหัวข้อ "สิ่งที่ไม่ทำ" ของ spec

## Test Environment / Precondition

- Web App responsive — ทดสอบทั้งบน desktop browser และ mobile browser (ตาม platform ที่ spec ระบุ)
- มีบัญชี User ทดสอบอย่างน้อย 1 บัญชีที่ผ่านการสมัครสมาชิกแล้ว และอย่างน้อย 1 เบอร์โทรที่ยังไม่เคยสมัคร
- มีข้อมูลราคากลางอ้างอิงต่อกิโลกรัมที่ Admin ตั้งไว้ล่วงหน้าอย่างน้อยครบ 5 ประเภทขยะ (กระดาษ/พลาสติก/เหล็ก/อลูมิเนียม/ขวดแก้ว)
- มีที่อยู่ทดสอบทั้งใน (เช่น ในเขตอำเภอเมือง เชียงราย) และนอกพื้นที่ให้บริการ (เช่น อำเภออื่นของเชียงราย หรือจังหวัดอื่น)
- มีคำขอทดสอบที่ครอบคลุมทุกสถานะ (รอ Admin ยืนยัน / รอสาเล้งรับงาน / รอ Admin confirm / ยืนยันแล้ว / เสร็จสิ้น / ยกเลิก) เตรียมไว้ล่วงหน้าสำหรับ test case ที่ต้องอ่านสถานะที่ user เองสร้างขึ้นเองไม่ได้ (ต้องมีฝั่ง Saleng/Admin ช่วย seed ข้อมูล)
- มีคำขอที่มีใบเสร็จจาก Saleng ส่งเข้ามาแล้วอย่างน้อย 1 รายการ (สำหรับทดสอบหน้าใบเสร็จ)

## Negative / Edge Cases

รวมอยู่ในตาราง Test Cases ของแต่ละหมวดข้างต้นแล้ว (ทำเครื่องหมายด้วยคำอธิบาย Scenario ที่ขึ้นต้นด้วยคำว่า "ผิด/ไม่ถูกต้อง/เกิน/ไม่สำเร็จ/นอกพื้นที่/ยกเลิก" เป็นหลัก) จุดที่เด่นที่สุดคือ:
- TC-001-018 / TC-001-020 — ที่อยู่นอกพื้นที่ให้บริการ (business rule สำคัญที่สุดของ MVP)
- TC-001-029 — อัปโหลดรูปเกิน 5 ภาพ
- TC-001-045 — no auto-expire ของคำขอที่ยังไม่มีสาเล้งรับงาน
- TC-001-044 — ปุ่มยกเลิกต้องไม่แสดงหลังงานเสร็จสิ้น/ยกเลิกแล้ว

## Open Items

1. **วิธียืนยันตัวตนของ User (เบอร์โทร + OTP)** — spec ไม่ได้ระบุวิธียืนยันตัวตนของ User ไว้ชัดเจน (ต่างจาก Saleng ที่ระบุชัดว่าใช้เบอร์โทร/OTP) prototype เลือกใช้แบบเดียวกันโดย inferred เท่านั้น หากทีมยืนยันวิธีอื่น (เช่น email/password) test case กลุ่ม TC-001-001 ถึง TC-001-009 ทั้งหมดต้องออกแบบใหม่
2. **การระบุตำแหน่งด้วยพิกัด GPS** — business rule ของ spec ระบุว่า User ระบุตำแหน่งได้ทั้ง "ที่อยู่ หรือพิกัด GPS" แต่ prototype หน้าเลือก/กรอกที่อยู่มีเฉพาะช่องกรอกที่อยู่แบบข้อความเท่านั้น ยังไม่มี UI สำหรับปักหมุด GPS จึงยังไม่มี test case รองรับการระบุตำแหน่งด้วยพิกัด GPS — รอ prototype ออกแบบ UI ส่วนนี้เพิ่มก่อนจึงจะแตก test case ได้
3. **ขนาด/ชนิดไฟล์รูปภาพที่อนุญาต** — spec และ prototype ระบุเพียงจำนวนสูงสุด 5 ภาพ แต่ไม่ได้ระบุขนาดไฟล์สูงสุดหรือชนิดไฟล์ (นามสกุล) ที่รองรับไว้ชัดเจน แม้ prototype จะมี error state "ไฟล์ผิดชนิด/เกินขนาด" จึงยังไม่สามารถระบุ test data ที่แม่นยำสำหรับกรณีนี้ได้ — ต้องยืนยันเงื่อนไขก่อน
4. **Breakdown ค่าธรรมเนียมในใบเสร็จ (platform fee)** — prototype หน้าใบเสร็จแสดง breakdown ค่าธรรมเนียม 20 บาทและยอดสุทธิให้ User เห็นโดย inferred จาก business rule เรื่องการหักเงินจาก user (สเปกไม่ได้ระบุตรงๆ ว่าต้องแสดงให้ user เห็นหรือไม่) หากทีมยืนยันว่าจะซ่อนรายละเอียดนี้จาก user ในภายหลัง TC-001-067 ต้องถูกทบทวนใหม่
5. **รูปแบบฟอร์มสร้างคำขอ (single-page vs multi-step)** — prototype เลือกออกแบบเป็น single-page scrollable form โดย inferred (ยังไม่ได้ confirm กับ user จริงตามที่บันทึกไว้ใน log วันที่ 2026-08-20) หากภายหลังเปลี่ยนเป็น multi-step wizard test case ในหมวด "4. ฟอร์มสร้างคำขอ" (TC-001-024 ถึง TC-001-037) อาจต้องปรับ steps ใหม่ให้ตรงกับ flow จริง
6. **Business rule ฝั่ง Admin/Saleng ที่กระทบสถานะฝั่ง User** (เช่น เงื่อนไข confirm 2 ขั้นของ admin-assign, ผลกระทบต่อคำขอค้างเมื่อ Saleng ถูกระงับบัญชี) ไม่อยู่ในสโคปของเอกสารนี้ตามที่ orchestrator กำหนด — หากมี test plan แยกฝั่ง Admin/Saleng ในอนาคต ควรตรวจสอบว่าผลลัพธ์ที่ User เห็น (เช่น สถานะเปลี่ยนเป็น "ยืนยันแล้ว") สอดคล้องกับ test plan ฝั่งนั้นด้วย

## สร้าง User Journey (Mermaid flowchart) ครบ 3 persona จาก Call-Saleng spec

- อ่าน [[../01-requirements/01-spec/20260819-001-saleng-pickup-request|Call-Saleng: ระบบเรียกรถซาเล้งมารับซื้อขยะ Recycle ที่บ้าน]] และ [[../01-requirements/feature-list|feature-list]] (มีอยู่แล้วครบ ไม่ต้องรอ feature-list-writer) ตรวจสอบ `docs/02-design/01-prototypes/` แล้วพบว่ามีแค่ `index.md` ยังไม่มี journey doc มาก่อน จึงสร้างไฟล์ใหม่ทั้งหมด 5 ไฟล์ (running no. 001–005)
- แตก persona/flow จากหัวข้อ "User stories / Use cases" และโครงสร้าง "หน้า" ต่างๆ ที่สเปกแยกไว้ชัดเจน ได้ทั้งหมด 5 journey เพราะ **Admin มีมากกว่า 1 flow ที่แยกจากกันชัดเจนในเนื้อหา** (ต่างหน้าจอ/บริบทกัน): จับคู่คำขอ, จัดการรถซาเล้ง, และจัดการราคากลาง ส่วน User และ Saleng มี flow เดียวที่ต่อเนื่องกันจริงจึงรวมเป็น 1 ไฟล์ต่อ persona:
  1. [[../02-design/01-prototypes/20260820-001-user-pickup-request-journey|User — Pickup Request Journey]] — ตั้งแต่สร้างคำขอ ตรวจสอบพื้นที่บริการ อัปโหลดรูป รอ Admin confirm รอสาเล้งรับงาน จนถึงเห็นใบเสร็จ
  2. [[../02-design/01-prototypes/20260820-002-saleng-job-fulfillment-journey|Saleng — Job Fulfillment Journey]] — ตั้งแต่ล็อกอิน ดูรายการงาน self-pick รอ Admin confirm ไปรับซื้อขยะ ปิดงาน ส่งใบเสร็จ จนถึง settle ค่าธรรมเนียม
  3. [[../02-design/01-prototypes/20260820-003-admin-request-matching-journey|Admin — Request Matching Journey]] — ตรวจคำขอ, confirm/cancel, แยกเส้นทาง admin-assign (confirm 2 ขั้น) vs self-pick, มาบรรจบที่ Admin confirm กับ user เป็นขั้นสุดท้ายเสมอ
  4. [[../02-design/01-prototypes/20260820-004-admin-saleng-management-journey|Admin — Saleng Account Management Journey]] — ครอบคลุม 4 ฟีเจอร์ของหน้าจัดการรถซาเล้ง (อนุมัติสมัครใหม่, ดูสถานะ, ดูประวัติงาน, ระงับบัญชี)
  5. [[../02-design/01-prototypes/20260820-005-admin-price-management-journey|Admin — Price Management Journey]] — flow สั้นไม่มีสาขาซับซ้อนสำหรับตั้ง/อัปเดตราคากลางอ้างอิงต่อกิโลกรัม
- ทุกไฟล์แทรก wikilink ไปยัง feature-list.md แบบอ้างอิง header ตาม persona (`#User`, `#Saleng`, `#Admin`) ที่จุดที่กล่าวถึงฟีเจอร์นั้นๆ เพราะ feature-list.md เป็นตารางไม่มี anchor ต่อแถว จึงลิงก์ที่ระดับ persona header แทน และอ้างอิง business rule จากสเปกตรงจุดตัดสินใจ (diamond node) ทุกจุด เช่น พื้นที่บริการ, no-auto-expire, กลไก 2 ขั้นของ admin-assign, ยืนยันตัวตนเบอร์โทร/OTP
- ใส่ node "รอการออกแบบเพิ่มเติม" ไว้ในหัวข้อ "เส้นทางอื่น / Edge case" ของแต่ละไฟล์ตรงจุดที่สเปกไม่ได้ระบุไว้ชัดเจน (ไม่ได้เดาเอง) ได้แก่: ผลกระทบต่อคำขอค้างเมื่อ user ถูกระงับบัญชี, กรณี Admin ปฏิเสธการจับคู่ self-pick, งานค้างอยู่ตอนสาเล้งถูกระงับบัญชี, ขั้นตอน/เงื่อนไขปลดระงับบัญชีสาเล้ง, ผลย้อนหลังของการเปลี่ยนราคากลางต่อคำขอเก่า
- ไม่ได้ใช้ AskUserQuestion ในรอบนี้ เพราะข้อมูลใน spec (business rules, user stories) เพียงพอต่อการวาด flow หลักได้อย่างสมเหตุสมผลโดยไม่ต้องเดารายละเอียดที่ไม่มีในสเปก — ประเด็นที่ไม่ชัดเจนถูกกำกับเป็น "รอการออกแบบเพิ่มเติม" แทน
- ไม่มีการแก้ไขเอกสาร spec ต้นทางหรือ feature-list.md ใดๆ — อ่านอย่างเดียวตามหน้าที่ของ user-journey-writer

- **Navigation pattern**: orchestrator ระบุว่า Admin ใช้งานผ่าน desktop เป็นหลัก จึงเลือกใช้ **sidebar navigation แนวตั้งด้านซ้าย** แทน bottom tab bar สำหรับทุกหน้าจอ Admin (DESIGN.md ไม่มีตัวอย่างเฉพาะ desktop มาก่อน) โดย adapt token สี/typography/spacing/radius เดิมมาใช้ทั้งหมด ไม่มีการเพิ่ม token ใหม่ — sidebar มี 3 เมนู: คำขอ / รถซาเล้ง / ราคากลาง ตรงกับ 3 กลุ่มหน้าจอ
- **การรวมหน้าจอ**: หน้า "จัดการรถซาเล้ง" (4 ฟีเจอร์ตามสเปก: อนุมัติสมัครใหม่, ดูสถานะ, ดูประวัติงาน, suspend) ออกแบบเป็น**ไฟล์เดียวแบบ master-detail** (list สาเล้งซ้าย + detail panel ขวา พร้อม tab "ข้อมูลทั่วไป"/"ประวัติงาน" ภายใน panel) แทนการแยกเป็นหลายไฟล์ เพราะพื้นที่ desktop กว้างพอให้เห็น context พร้อมกันโดยไม่ต้อง navigate ไปมา — บันทึกเหตุผลไว้ในหัวข้อ "อ้างอิงจาก" ของไฟล์นั้น รวมหน้าจอทั้งหมดจึงเป็น 4 ไฟล์ตามสโคปขั้นต่ำที่ orchestrator กำหนด
- หน้ารายละเอียดคำขอ (#018) ออกแบบ action panel แบบ vertical timeline stepper ที่เปลี่ยนปุ่ม action ตามสถานะปัจจุบัน ครอบคลุมทั้ง 2 เส้นทางจับคู่งาน: admin-assign (ต้อง confirm 2 ขั้น — เลือกสาเล้งแล้ว confirm กับสาเล้งก่อน จากนั้น confirm กับ user อีกครั้ง) และ self-pick (รอสาเล้งกดรับงานเอง แล้ว Admin confirm ขั้นสุดท้ายกับ user) ตาม business rule ที่ระบุไว้ตรงๆ ในสเปก ไม่ใช่ inferred — แชทกับ user ออกแบบเป็น drawer เลื่อนเข้าจากขวาทับหน้าเดิม แทนที่จะแยกเป็นหน้าใหม่ เพราะ Admin มักต้องสลับดูรายละเอียดคำขอไปพร้อมกับแชท ต่างจากหน้าแชทของ User/Saleng ที่แยกเป็นหน้าเต็ม

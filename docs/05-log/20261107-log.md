## อัปเดต requirement 002 — ปิด Open questions การจับคู่งานสาเล้ง และเปิด scope ฝั่งสาเล้ง

- **เอกสารที่แก้ไข:** [[../01-requirements/01-spec/20260912-002-saleng-auto-matching|20260912-002-saleng-auto-matching]] (แก้ไขเอกสารเดิม ไม่สร้างใหม่) และ sync แถวเดิมใน [[../01-requirements/backlog|backlog]] (สถานะ New → Confirmed, วันที่แก้ไขล่าสุด 2026-11-07)
- **เหตุผลที่แก้ไขเดิมแทนสร้างใหม่:** ข้อสรุปทั้งหมดเป็นคำตอบของ Open questions ในเอกสาร 002 โดยตรง และอยู่ในเรื่องเดียวกัน (การจับคู่งานสาเล้ง) ส่วนที่ขยายเพิ่ม (อนุมัติสาเล้ง, โควตา, การยกเลิก, แชท Admin–สาเล้ง) เป็น rule ที่ผูกกับ flow การจับคู่เดียวกัน — คงชื่อไฟล์เดิมเพื่อไม่ให้ wikilink เสีย แต่ปรับชื่อหัวเรื่องเป็น "ระบบจับคู่งานสาเล้งตามพื้นที่ (ตำบล) + Admin-assign และการจัดการสาเล้ง (เดิมชื่อ Auto-Matching)" เพราะตัด GPS/auto ออกแล้ว
- **ข้อสรุปที่ user ยืนยันในแชท (ไม่ได้ถามซ้ำ):**
  1. จับคู่ตามตำบล (`sub_district`) + Admin-assign (manual) ตัด GPS ("ฉันเลือก 1+3 เรื่อง gps ตัดทิ้งก่อน")
  2. สาเล้งเห็นเฉพาะงาน `open_for_saleng` ในตำบลที่ลงทะเบียน (หลายตำบลได้) งานตำบลอื่นต้อง Admin-assign; Admin dashboard เตือนงานในตำบลที่ไม่มีสาเล้ง/ค้างนาน
  3. คง Admin confirm ขั้นสุดท้าย; flow `pending_admin_review → open_for_saleng → pending_match_confirm → confirmed → completed`; แชท Admin–สาเล้งแยกจากแชทลูกค้า
  4. งาน admin-assign สาเล้งต้องกดตอบรับ/ปฏิเสธก่อนรอ Admin confirm
  5. การยกเลิกของสาเล้ง: งานกลับเป็น `open_for_saleng`; ก่อน confirm ยกเลิกอิสระ; หลัง confirm ยกเลิกเองได้ถึง เริ่มรอบนัด − min(6 ชม., ครึ่งหนึ่งของเวลาตั้งแต่กดรับถึงเริ่มรอบนัด); เลยกำหนดต้องขอผ่าน Admin ทางแชท; ต้องมีเหตุผล; นับสถิติยกเลิกกระชั้นชิด; ลูกค้าเห็นแจ้งเตือนว่ากำลังหาซาเล้งใหม่
  6. สมัครสาเล้ง (ชื่อ, เบอร์, ทะเบียนรถ, รูปรถ, รูปบัตรประชาชน, ตำบล) → `pending_approval` → approve/reject (มีเหตุผล) → `approved`; `suspended` ภายหลัง; รูปบัตรประชาชนอ่านได้เฉพาะเจ้าของ+Admin และระบบทดสอบใช้รูปจำลอง
  7. โควตา: ≤ 3 งาน/รอบ (วัน+ช่วงเวลาเดียวกัน), ≤ 6 งานค้างรวม; Admin เห็นโควตาและ override ได้พร้อมคำเตือน; รายชื่อตอน assign เรียงตำบลตรงก่อนแล้วคิวน้อยก่อน
  8. ฝั่งสาเล้งใช้บน smartphone (Web App responsive)
- **ขอบเขต:** user สั่งเริ่มพัฒนาหน้าซาเล้งแล้ว — ปรับหมายเหตุในเอกสาร 002 จาก "อยู่นอกขอบเขตโมดูลปัจจุบัน" เป็น "เปิด scope ฝั่งสาเล้งในรอบพัฒนานี้แล้ว"
- **จุดที่ spec หลักควรปรับตาม (บันทึกไว้ ไม่ได้แก้ [[../01-requirements/01-spec/20260819-001-saleng-pickup-request|spec หลัก 001]] โดยตรง):**
  - **ขัดโดยตรง:** spec หลักกำหนดยืนยันตัวตนสาเล้งด้วยเบอร์โทร/OTP เท่านั้น ไม่ต้องอัปโหลดทะเบียนรถ/บัตรประชาชน และใส่ KYC ไว้ใน Out of scope — ข้อสรุปใหม่เพิ่มทะเบียนรถ/รูปรถ/รูปบัตรประชาชนในการสมัคร (user ยืนยันเองชัดเจน จึงไม่ได้ถามซ้ำ)
  - ปรับถ้อยคำให้ตรงกัน: ขั้น "Admin confirm กับสาเล้ง" ใน admin-assign → สาเล้งกดตอบรับ/ปฏิเสธ; การมองเห็นงานจำกัดเฉพาะตำบลที่ลงทะเบียน; การยกเลิกของสาเล้งมีกำหนดเวลาและคืนงานเป็น `open_for_saleng`
  - `SCOPE.md` / `CLAUDE.md` ที่ root ยังระบุว่าฝั่งสาเล้งอยู่นอกขอบเขต; [[../02-design/02-technical/database-schema|database-schema]] ต้องเพิ่ม field รองรับ (รายละเอียดในหัวข้อ "ผลกระทบต่อเอกสารอื่น" ของเอกสาร 002)
- **ประเด็นติดตามต่อ (ระดับออกแบบ):** เกณฑ์ "งานค้างนาน", นิยาม "ยกเลิกกระชั้นชิด", ผลของ Admin เปลี่ยนเวลานัดต่อกำหนดยกเลิก/โควตา, การกันงานระหว่างรอสาเล้งตอบรับ assign, วิธี login ของสาเล้ง, การแจ้งเตือนแบบ push/badge
- ไม่มีการแก้ไฟล์ใน `webapp/` หรือ `firestore.rules` และไม่มีการ commit

## อัปเดต database-schema และ api-spec ตาม requirement 002 (ฝั่งสาเล้ง/การจับคู่ที่พัฒนาแล้ว)

- **เอกสารที่แก้ไข (ต่อยอดของเดิม ไม่ rewrite):** [[../02-design/02-technical/database-schema|database-schema]] และ [[../02-design/02-technical/api-spec|api-spec]] — ที่มา: [[../01-requirements/01-spec/20260912-002-saleng-auto-matching|spec 002]] (Business rules + "ผลกระทบต่อเอกสารอื่น" ข้อ 7) ประกอบ [[../01-requirements/01-spec/20260819-001-saleng-pickup-request|spec หลัก 001]] โดยให้ field/สถานะเชิงแนวคิดตรงกับสิ่งที่ implement แล้ว แต่ยังคงเป็น conceptual/technology-agnostic
- **database-schema:**
  - `saleng_account` เพิ่ม `vehicle_plate`, `service_sub_districts` (หลายค่า), `reject_reason`, `reviewed_at/by`, แยก `suspended_at/by` กับ `suspend_reason`; ทำเครื่องหมาย `otp_verification_status` ว่าไม่ใช้ใน MVP (login เบอร์โทร+รหัสผ่าน) แต่ไม่ลบ; หมายเหตุสิทธิ์ "สาเล้งที่ใช้งานได้" (approved + active)
  - ตารางใหม่ `saleng_document` (รูปรถ/รูปบัตรประชาชน, ข้อมูลอ่อนไหว, ระบบทดสอบใช้รูปจำลอง) และ `saleng_chat_message` (แชท Admin–สาเล้งต่อคำขอ แยกจาก `chat_message`)
  - `pickup_request` เพิ่มกลุ่ม field การจับคู่ที่ denormalize (`assigned_saleng_name/phone/plate`, `match_channel`, `saleng_accepted`, `assigned_at`, `accepted_at`, `active_match_id`, `match_confirmed_at` แทน `final_confirmed_at/by`) และ `opened_at`; ระบุ flow สถานะครบ 6 ค่า + การคืนงานเป็น `open_for_saleng`
  - `request_match` ชุดสถานะใหม่ (`pending_saleng_accept` แทน `pending_admin_confirm_saleng`; `superseded` คงไว้แต่ยังไม่ใช้), เพิ่ม `created_by`, `accepted_at`, `ended_by/end_reason/ended_at` (แทน `rejected_*`), `cancelled_after_confirm`
  - ER diagram + "สมมติฐานและข้อจำกัด" (โควตา 3/รอบ + 6 ค้างรวม, สูตรกำหนดเวลายกเลิก, การมองเห็นตามตำบล, งาน assign ที่ยังไม่ตอบรับถูกกันไว้/นับโควตา/ไม่มี timeout, งานค้าง > 2 ชม.)
  - ปิดคำถามเปิดข้อ 1, 6 และปิดบางส่วนข้อ 3, 4; เพิ่มคำถามใหม่ข้อ 8–12
- **api-spec:** Saleng Account (register พร้อมเอกสาร, view_own_status, view_documents, approve/reject/suspend/reactivate — reject/suspend บังคับเหตุผล; request_otp/verify_otp ไม่ใช้ใน MVP), Pickup Request (list_open กรองตำบลและซ่อนที่อยู่/เบอร์ลูกค้า, list_my_jobs, list_attention, complete; ย้าย cancel (saleng) ไป Request Match), Request Match (self_pick กันชน+โควตา, list_assign_candidates, assign+override, accept/decline_assignment, confirm, cancel_by_saleng พร้อมกำหนดเวลา, release, list_cancel_stats), resource ใหม่ Saleng Chat Message, อัปเดต Actors/สมมติฐาน/คำถามเปิด

## อัปเดต High-Level Architecture ตามคำตอบ AskUserQuestion ของ orchestrator (2 ข้อที่ค้างไว้)

- Orchestrator ส่งคำตอบของ user กลับมาในวันเดียวกัน (2026-08-25) หลัง confirm ผ่าน AskUserQuestion ของ orchestrator เอง (ไม่ใช่ของ agent นี้โดยตรง เพราะ agent ไม่มี tool นี้พร้อมใช้งานตอนร่างครั้งแรก) สำหรับ 2 สมมติฐานที่ตั้งไว้ในรอบก่อนหน้า:
  1. **Matching/Assignment** → user เลือก "แยกเป็น component ต่างหากตั้งแต่ตอนนี้" (ตรงข้ามกับสมมติฐานเดิมที่ร่างไว้ว่าให้รวมกับ Core Application Layer) เหตุผลคือเตรียมพร้อมรองรับ auto-matching ในอนาคตโดยไม่ต้องรื้อโครงสร้างทีหลัง
  2. **Media/File Storage** → user ยืนยัน "แยกจาก Data Store" ตามที่ร่างไว้เดิม ไม่ต้องเปลี่ยน logic ใดๆ แค่ปรับ wording ใน "สมมติฐานและข้อจำกัด" จาก "agent ตัดสินใจเอง" เป็น "user ยืนยันแล้ว"
- แก้ไข [[../02-design/02-technical/high-level-architecture|High-Level Architecture (Conceptual)]] ด้วย Edit (ไม่ rewrite ทั้งไฟล์) ตามคำตอบข้อ 1 ครบทุกจุดที่เกี่ยวข้อง:
  - เพิ่ม **Matching/Assignment** เป็น conceptual component ใหม่ในหัวข้อ "Conceptual Components" รับผิดชอบเฉพาะกลไกจับคู่งาน (self-pick/admin-assign, บังคับกฎ 1 คำขอต่อ 1 สาเล้ง, ป้องกันรับงานซ้ำ) และปรับขอบเขตของ Core Application Layer ให้เหลือเฉพาะ auth/สิทธิ์, วงจรชีวิตคำขอ (สร้าง/confirm/cancel/เสร็จสิ้น), ตรวจพื้นที่บริการ, คำนวณค่าธรรมเนียม, จัดการราคากลาง — ไม่รวม logic การจับคู่แล้ว
  - เพิ่ม node `MATCH[Matching/Assignment]` ใน System Context diagram (Mermaid flowchart) พร้อมปรับเส้นเชื่อม: Core Application Layer → Matching/Assignment → Data Store
  - ปรับ sequence diagram ของ journey ที่ 1 (User), 2 (Saleng), 3 (Admin) ให้ message ที่เกี่ยวกับ self-pick/admin-assign/ตรวจสอบว่าคำขอถูกรับไปแล้วหรือยัง/confirm การจับคู่ ไปที่ participant ใหม่ `Matching` แทน `Core` ตรงๆ (journey ที่ 4, 5 ไม่แตะเพราะไม่เกี่ยวกับ matching ตามที่ orchestrator ระบุ)
  - ปรับ prose ใต้ diagram ของ journey ที่ 1, 2, 3 ให้กล่าวถึง Matching/Assignment component แทนจุดที่เคยบอกว่า Core Application Layer จัดการเอง
  - หัวข้อ "สมมติฐานและข้อจำกัด": เปลี่ยนข้อ Matching/Assignment จาก "agent ตัดสินใจเอง (ไม่แยก)" เป็น "user ยืนยันเมื่อ 2026-08-25 ให้แยกเป็น component ต่างหาก" พร้อมเหตุผลเรื่อง auto-matching ในอนาคต และเปลี่ยนข้อ Media/File Storage จาก "agent ตัดสินใจเอง" เป็น "user ยืนยันแล้ว (คงตามเดิม)"
  - หัวข้อ "คำถามเปิด": ลบข้อ 6–7 ออก (ได้คำตอบแล้ว) เหลือ 5 ข้อเดิมจาก edge case ของ journey docs
- ไม่มีการแก้ไข spec ต้นทาง, feature-list.md, หรือ journey doc ใดๆ ในรอบนี้เช่นกัน — แก้ไขเฉพาะ `high-level-architecture.md` ตามหน้าที่ของ architecture-writer

## สร้าง Database Schema และ API Spec (Conceptual) ฉบับแรก — ครอบคลุมทั้ง 3 บทบาท

- Orchestrator (skill `generate-data-api-spec`) confirm scope กับ user แล้วว่าให้ทำทั้งระบบ (spec เดียว `20260819-001-saleng-pickup-request` ครอบคลุม User/Saleng/Admin) ตรวจสอบ `docs/02-design/02-technical/` แล้วพบว่ายังไม่มีไฟล์ `database-schema.md` และ `api-spec.md` มาก่อน จึงสร้างใหม่ทั้งสองไฟล์:
  - [[../02-design/02-technical/database-schema|Database Schema (Conceptual)]] — สกัด entity ได้ 17 ตาราง แบ่ง 7 กลุ่ม (บัญชี 3 บทบาท, คำขอ+รายละเอียดประกอบ, ราคากลางอ้างอิง, การจับคู่งาน, ใบเสร็จ+ค่าธรรมเนียม, การสื่อสาร, เผื่อรองรับอนาคตแบบ minimal — `membership_tier`, `ad_banner`) พร้อม ER diagram (Mermaid `erDiagram`) และตารางฟิลด์ครบทุกตาราง
  - [[../02-design/02-technical/api-spec|API Spec (Conceptual Data Contract)]] — แปลง entity เป็น 11 resource พร้อม operation ต่อ actor (User/Saleng/Admin) ครบตาม user story ทั้ง 20 ข้อในสเปก โดยเฉพาะ resource **Request Match** ที่แยกจาก **Pickup Request** ตรงตาม Matching/Assignment component ที่ user ยืนยันแยกไว้แล้วใน high-level-architecture
- อ้างอิง [[../01-requirements/01-spec/20260819-001-saleng-pickup-request|Call-Saleng spec]] (ต้นทางหลัก), [[../01-requirements/feature-list|feature-list]], [[../02-design/02-technical/high-level-architecture|high-level-architecture]] (ใช้ชื่อ component ให้สอดคล้อง เช่น Matching/Assignment → ตาราง/resource `request_match` แยกต่างหาก) และ journey doc ครบทั้ง 5 ฉบับเพื่อสกัด state/operation ให้ครบ
- **ไม่มี AskUserQuestion tool พร้อมใช้งานในสภาพแวดล้อมนี้** (เช่นเดียวกับที่ระบุไว้ใน log ของ high-level-architecture) จึงตัดสินใจแทนในประเด็นที่ไม่ชัดเจนโดยให้เหตุผลไว้ในหัวข้อ "สมมติฐานและข้อจำกัด" ของทั้งสองไฟล์ และรวบรวมเป็น "คำถามเปิด" ให้ orchestrator/user ยืนยันภายหลัง ประเด็นสำคัญ:
  1. โครงสร้างข้อมูลการจับคู่งาน — เลือกแยกตาราง `request_match` ต่างหากจาก `pickup_request` (แทนเก็บเป็น field ตรง) เพื่อรองรับ edge case เปลี่ยน/ปฏิเสธการจับคู่ที่ journey doc ระบุว่ารอการออกแบบเพิ่มเติม
  2. ผลกระทบต่องาน/คำขอค้างเมื่อบัญชีถูกระงับระหว่างทาง — เลือก "ไม่กระทบงานที่ confirmed ไปแล้วอัตโนมัติ" เป็นค่าเริ่มต้นที่กระทบน้อยที่สุด
  3. ราคากลาง — เลือกไม่มี audit trail แบบตารางประวัติแยก และคำขอไม่เก็บ snapshot ราคา (ราคาอ้างอิงเท่านั้น ไม่ผูกธุรกรรม)
  4. ระดับ normalize ประเภทขยะ — เลือกตารางอ้างอิง `waste_type` ใช้ร่วมกันทั้งคำขอ/ราคากลาง/ใบเสร็จ เพราะ Admin ต้องจัดการราคาต่อประเภทอยู่แล้ว
  5. `pickup_request_waste_item` ออกแบบให้เลือกได้หลายประเภทต่อ 1 คำขอ (ตีความจาก background ของสเปกที่ขยะมักปนกันหลายประเภท)
  6. เพิ่ม field `sub_district` (ตำบล) ในที่อยู่/คำขอ เพื่อรองรับ filter "พื้นที่ที่สนใจ" ของสาเล้งตาม journey doc
  7. `Request Match.reject` และ `unsuspend`/`top_up_wallet` เป็น operation ที่อนุมานเพิ่มเพื่อความสมบูรณ์ของ flow (ไม่มีในสเปกตรงๆ) — ระบุเป็นสมมติฐานชัดเจนในเอกสาร
- เผื่อรองรับโมเดลธุรกิจ 3 ช่องทางรายได้ตามที่สเปกระบุไว้ใน "โมเดลธุรกิจ/รายได้": ค่าบริการเรียกใช้งาน (เต็มรูปแบบใน MVP ผ่าน `saleng_fee_ledger_entry`/`saleng_wallet_balance`), ค่าโฆษณา (`ad_banner` — minimal placeholder), ค่าสมาชิกรายเดือน (`membership_tier` — minimal placeholder) โดยระบุหมายเหตุกำกับชัดเจนว่า 2 อย่างหลังเป็นการเผื่อรองรับอนาคต ไม่ใช่ฟีเจอร์ที่พัฒนาจริงใน MVP
- อัปเดต [[../02-design/02-technical/index|02-technical]] เพิ่มลิงก์ไปยัง `database-schema.md` และ `api-spec.md` (คงเนื้อหาเดิมของไฟล์ไว้ครบ)
- ไม่มีการแก้ไข spec ต้นทาง, feature-list.md, journey doc, หรือ high-level-architecture.md ใดๆ — อ่านอย่างเดียวตามหน้าที่ของ data-api-spec-writer

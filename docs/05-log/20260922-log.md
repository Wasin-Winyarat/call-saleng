- อ่านโค้ด webapp/profile/app.js และ webapp/pickup-request/app.js พบว่า:
  - บันทึกที่อยู่ของผู้ใช้เป็น **2 ช่องคงที่เท่านั้น** (address_1 และ address_2) เก็บเป็น map field ภายในเอกสาร Firestore เดียวของผู้ใช้
  - ไม่มี UI ให้เพิ่มที่อยู่ได้มากกว่า 2 ช่อง
- เทียบกับ [[../02-design/02-technical/database-schema|database-schema.md]] ซึ่งออกแบบ `user_address` เป็น **collection แยก** (1-to-many unbounded) ทำให้สามารถเก็บที่อยู่ได้เท่าไหร่ก็ได้
- **ความเบี่ยงเบน**: webapp ใช้การจำลองที่กระชับขึ้น (bounded, fixed 2 slots) แทนเอกสารออกแบบที่เสนอแนวทางไม่จำกัด
  - ไม่มีข้อบ่งชี้ใน webapp code ว่าทำไมจึงเลือก 2 ช่องคงที่ (เป็นตัดสินใจขณะ implement หรือตั้งใจจากเริ่มต้น?)
  - ต้องปรึกษาผู้ใช้/coordinator ว่าข้อจำกัดนี้เป็นจงใจหรือชั่วคราว และต้องอัปเดต database-schema.md หรือไม่

## ปิดประเด็น max-2-addresses ใน database-schema.md — ยืนยันเป็น business rule จริง

- ตรวจสอบ requirement spec ต้นทาง ([[../01-requirements/01-spec/20260819-001-saleng-pickup-request|20260819-001-saleng-pickup-request]]) พบว่าไม่มีการระบุจำนวนที่อยู่บันทึกไว้สูงสุดตรงๆ — เดิม [[../02-design/02-technical/database-schema|database-schema.md]] ออกแบบ `user_address` เป็น 1-to-many แบบไม่จำกัดจำนวน ต่างจากที่ `webapp/profile/app.js`/`webapp/pickup-request/app.js` ใช้จริง (2 ช่องคงที่ `address_1`/`address_2`)
- ถามผู้ใช้ว่าจำนวน "2" นี้เป็น business decision จริงหรือแค่ implementation shortcut โดยเสนอ 3 ทางเลือก (encode เป็น constraint / ไม่แก้อะไร / บันทึกเป็นคำถามเปิดเฉยๆ)
- **ผู้ใช้ยืนยันแล้ว**: เลือกทางเลือกที่ 1 — "2" เป็น business decision จริง ให้เพิ่มเป็น constraint ในเอกสาร conceptual
- แก้ไข [[../02-design/02-technical/database-schema|database-schema.md]]:
  - ปรับ label ความสัมพันธ์ใน ER diagram: `user_account ||--o{ user_address` เพิ่มหมายเหตุ "(สูงสุด 2 รายการ/user)"
  - เพิ่ม prose "Business rule (ยืนยันแล้ว)" และแถว `Constraint:` ใต้ตารางฟิลด์ในหัวข้อ `### user_address` ระบุจำนวนแถวต่อ `user_id` ไม่เกิน 2
  - เพิ่ม bullet ใหม่ในหัวข้อ "สมมติฐานและข้อจำกัด" อธิบายที่มาของ constraint นี้ (ไม่มีใน spec ตรงๆ แต่ยืนยันจากผู้ใช้แล้ว) และระบุว่าประเด็นนี้ปิดแล้ว ไม่ใช่ "คำถามเปิด"
  - จุดอื่นตามการตรวจสอบเดิม (`saved_address_id` เป็น slot label เชิง implementation, และ 4 รายการ collection ที่ยังไม่ implement) ยืนยันว่าไม่ต้องแก้เอกสาร — ตรงกับที่ออกแบบไว้แล้ว

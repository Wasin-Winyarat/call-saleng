## สร้าง Non-Functional Requirements (NFR) ฉบับแรก

- User ขอให้แนะนำ non-functional requirement โดยอ้างอิงจาก requirement/backlog/feature-list/test case/test report/high-level design/detailed design ที่มีอยู่ทั้งหมด พร้อมเหตุผลและทางเลือกอื่น (ถ้ามี) แสดงเป็นตาราง — สำรวจเอกสารทั้งหมดใน `docs/01-requirements/`, `docs/02-design/`, `docs/03-testing/` ก่อนสรุป (ไม่มี agent/skill เฉพาะสำหรับ NFR ในโปรเจกต์นี้ จึงทำโดยตรงในแชทแทน)
- พบว่า `docs/03-testing/02-test-result/` ยังเป็น index เปล่า ไม่มีผลทดสอบจริง และมีเพียง test plan ฝั่ง User เท่านั้น (ยังไม่มี Saleng/Admin) — ใช้เป็นหลักฐานว่ายังไม่มีบั๊ก/reliability gap ที่บันทึกไว้จริง แต่ open item ของ test plan (เช่น ไม่มี photo file size/type limit) ถูกยกมาเป็น NFR ตรงๆ
- ประเด็น NFR ที่ต้องใช้ดุลยพินิจทางธุรกิจ (ไม่มีข้อมูลในเอกสารต้นทางเลย) ถูกถามผู้ใช้ผ่าน AskUserQuestion 2 รอบ:
  1. รอบแรก: หมวด NFR ที่ควรมีทั้งหมด (16 หมวด) — user รับทราบและไม่มีการแก้ไข
  2. รอบสอง: 4 ประเด็นเชิงตัวเลข — บริบทการใช้งาน (**เลือก: ต้นแบบ/งานศึกษา**), ระดับ scale (**เลือก: pilot เล็ก <100 concurrent, <50 คำขอ/วัน**), uptime (**เลือก: best-effort เฉพาะช่วงเวลาให้บริการ 08:00-18:00**), ความถี่ polling (**เลือก: ทุก 15-30 วินาที**)
- สร้าง [[../02-design/02-technical/non-functional-requirements|Non-Functional Requirements (NFR)]] ใหม่ทั้งไฟล์ ครอบคลุม 16 หมวด แบ่งเป็น 2 กลุ่ม: (ก) NFR ที่ผูกกับ business rule ที่ระบุไว้แน่นอนแล้วในเอกสารอื่น เช่น atomic self-pick ([[../02-design/02-technical/high-level-architecture|high-level-architecture]]/[[../02-design/02-technical/database-schema|database-schema]]), การเผยข้อมูลติดต่อเฉพาะคู่ที่จับคู่แล้ว, financial ledger integrity — ยกระดับเป็นข้อกำหนดที่วัดผลได้โดยไม่ต้องถามซ้ำ (ข) NFR ที่ต้องใช้ดุลยพินิจทางธุรกิจ (scale, uptime, polling, compliance) — ยืนยันกับ user แล้วตามข้างต้นก่อนเขียนเป็นตัวเลขจริงในเอกสาร
- แต่ละหมวดมีตาราง "ข้อกำหนด / เหตุผล / ทางเลือกอื่นที่พิจารณา (พร้อมข้อดี-ข้อเสีย)" ตามที่ user ขอ พร้อมตารางสรุปรวม 16 แถวไว้ต้นเอกสาร
- คำถามเปิดที่เหลือ (ยังไม่มีตัวเลขแน่นอน): ขนาด/ประเภทไฟล์รูปสูงสุด, จำนวนครั้ง OTP ผิดก่อน lockout, browser/OS version list ที่ต้องทดสอบจริง, ระยะเวลา backup retention — และย้ำว่าต้องทวนสอบ uptime/scale/compliance/backup ใหม่ทั้งหมดถ้าโปรเจกต์เปลี่ยนทิศทางไปสู่การเปิดใช้งานจริง
- อัปเดต [[../02-design/02-technical/index|02-technical]] เพิ่มลิงก์ไปยัง `non-functional-requirements.md`
- ไม่มีการแก้ไข spec ต้นทาง, feature-list.md, journey doc, high-level-architecture.md, database-schema.md, api-spec.md, detailed-design, หรือ test plan ใดๆ — อ่านอย่างเดียวเพื่อสกัด NFR

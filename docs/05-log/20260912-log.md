# Log — 2026-09-12

## บันทึกไอเดีย auto-matching สาเล้งเป็น requirement spec ใหม่ (future/next-phase)

- ระหว่างคุยเรื่องแผนพัฒนาโมดูลปัจจุบัน user เสนอไอเดียเพิ่มเติมว่าอาจใช้ API หรือกลไกจับคู่คำขอกับสาเล้งที่อยู่ในพื้นที่แบบอัตโนมัติ (ด้วย GPS หรือตำบลที่สาเล้งลงทะเบียนพื้นที่สนใจไว้) แล้ว "เด้งงาน" ไปให้สาเล้ง confirm รับงานเอง (ไม่ใช่ auto-assign แบบบังคับ)
- Coordinator ชี้แจงว่าฟีเจอร์นี้อยู่นอกขอบเขตของโมดูลที่กำลังพัฒนาส่งอยู่ตอนนี้ตาม `SCOPE.md`/`CLAUDE.md` (โมดูลปัจจุบันคือ "User สร้างคำขอเรียกรถซาเล้ง" + "Admin accept/cancel/change-time" เท่านั้น ตัด flow ฝั่งสาเล้งออกทั้งหมด) และเสนอให้ร่างเป็น requirement spec ใหม่ไว้ก่อนแทนการ implement เลย — user ยืนยันให้ร่างเป็น requirement spec ใหม่ผ่าน skill `create-requirement`
- **เหตุผลที่สร้างเอกสารใหม่ (ไม่แก้ไขเอกสารเดิม)**: แม้จะต่อยอดจาก [[../01-requirements/01-spec/20260819-001-saleng-pickup-request|Call-Saleng: ระบบเรียกรถซาเล้งมารับซื้อขยะ Recycle ที่บ้าน]] แต่เป็น feature/scope ที่แยกจากเดิมชัดเจน (เกี่ยวข้องกับฝั่งสาเล้ง/matching ที่ทั้งสเปกหลักและโมดูลปัจจุบันตัดออกไปแล้ว) อีกทั้งเอกสารเดิมมีสถานะ "Confirmed — ยืนยันครบทุกประเด็นแล้ว ไม่มี Open question เหลือ พร้อมแตกไป 02-plan/02-technical" การเพิ่มเนื้อหาที่ยังไม่ตัดสินใจ (มี Open question ค้าง) เข้าไปในเอกสารที่ปิดประเด็นครบแล้วจะทำให้สถานะนั้นไม่ถูกต้อง จึงสร้างไฟล์ใหม่แยกต่างหากดีกว่า
- สร้างไฟล์ใหม่ [[../01-requirements/01-spec/20260912-002-saleng-auto-matching|ระบบจับคู่คำขอเรียกรถซาเล้งกับสาเล้งในพื้นที่แบบอัตโนมัติ (Auto-Matching)]] ระบุสถานะเป็น future/next-phase requirement ที่ยังไม่อยู่ใน sprint ปัจจุบัน ครอบคลุม:
  - บริบทที่มาของไอเดียและขอบเขตโมดูลปัจจุบันที่ไม่รวมฟีเจอร์นี้
  - Scope: จับคู่อัตโนมัติหลัง Admin confirm คำขอ (`open_for_saleng`) แล้วแจ้งเตือนสาเล้งในพื้นที่ ให้สาเล้งยังต้องกด confirm รับงานเอง (ไม่ใช่ auto-assign บังคับ)
  - อ้างอิงร่องรอยที่มีอยู่แล้วใน [[../02-design/02-technical/database-schema|database-schema]]: field `sub_district` ถูกเผื่อไว้ใน `user_address`/`pickup_request` แล้วสำหรับแนวทางจับคู่ตามตำบล แต่ยังไม่มีร่องรอยใดๆ สำหรับแนวทาง GPS ของสาเล้ง และยังไม่มี collection `saleng_account`/`request_match` implement จริงในระบบ
  - **Open question หลักที่ยังคงไว้ไม่ตัดสินใจแทน user**: จะจับคู่ด้วยตำบล (`sub_district`) หรือ GPS หรือทั้งสองแบบร่วมกัน (fallback) — ระบุข้อดี/ข้อเสียของแต่ละแนวทางไว้ในเอกสาร รอ user ยืนยันในรอบถัดไปก่อนแตกไปเป็น 02-plan/02-technical
- ไม่ได้ใช้ AskUserQuestion ในรอบนี้ เนื่องจาก coordinator ระบุมาชัดเจนแล้วว่าให้สร้างไฟล์ใหม่ (ไม่ใช่แก้ไขเอกสารเดิม) และให้คง Open question เรื่องวิธีจับคู่ (ตำบล/GPS/ทั้งสอง) ไว้อย่างชัดเจนโดยไม่ตัดสินใจแทน user — จึงไม่มีจุดคลุมเครือเพิ่มเติมที่ต้องถามในรอบนี้
- อัปเดต [[../01-requirements/backlog|backlog]]: เพิ่มแถวใหม่สำหรับ requirement นี้ สถานะ "New (Future/next-phase — นอกขอบเขตโมดูลปัจจุบันทั้งหมด)" วันที่สร้าง/แก้ไขล่าสุด 2026-09-12 พร้อมสรุปสั้นๆ และ Open question หลัก
- ไม่ได้แก้ไขเอกสาร [[../02-design/02-technical/index|02-technical]] (`database-schema.md`) หรือโค้ดใน `webapp/` ในรอบนี้ เนื่องจากอยู่นอกขอบเขตหน้าที่ของ requirement-writer และฟีเจอร์นี้ยังไม่ผ่านการยืนยัน Open question หลัก — ทีมออกแบบควรรอการยืนยันแนวทางจับคู่จาก user ก่อนเริ่มออกแบบ schema/architecture เพิ่มเติมสำหรับฟีเจอร์นี้
